Configure pipelines
Configure the basic settings for a pipeline, including source code, target catalog and schema, compute, and pipeline mode, in the workspace UI.
Databricks recommends developing new pipelines using serverless. For configuration instructions for serverless pipelines, see

.
The configuration instructions in this page use

. For instructions for configuring pipelines with legacy
Hive metastore

This page discusses functionality for the current default publishing mode for pipelines. Pipelines created before February 5, 2025 might use the legacy publishing mode and

The UI has an option to display and edit settings in JSON. You can configure most settings with either the UI or a JSON specification. Some advanced options are only available using the JSON configuration.

Pipeline settings
​
Pipeline settings fall into two categories:
Source code
: The collection of files that declare datasets using pipeline syntax. See
Configure source code
.
Infrastructure
: Settings that control compute, how updates are processed, and where tables are stored.
Most settings have reasonable defaults, but two require attention before running in production:
Target catalog and schema
: To make data available outside the pipeline, declare a target catalog and schema. Data is published to
Unity Catalog
by default. See
Set the target catalog and schema
.
Data access
: The compute used for execution must have permissions configured for your data sources and, if specified, a storage location.

​
To configure a new pipeline, do the following:
At the top of the sidebar, click

At the top, give your pipeline a unique name.
Under the name, you can see the default catalog and schema that have been chosen for you. Change these to give your pipeline different defaults.
The default

Select your preferred option to create a pipeline:

Start with sample code in Python

When you make your selection, you are redirected to the newly created pipeline.

Set the run-as user
​
Run-as user allows you to change the identity that a pipeline uses to run, and the ownership of the tables it creates or updates. This is useful in situations where the original user who created the pipeline has been deactivated, for example, if they left the company. In those cases, the pipeline can stop working, and the tables it published can become inaccessible to others. By updating the pipeline to run as a different identity, such as a service principal, and reassigning ownership of the published tables, you can restore access and ensure the pipeline continues to function. Running pipelines as service principals is considered a best practice because they are not tied to individual users, making them more secure, stable, and reliable for automated workloads.

How to set the run-as user
​
You can set the
run-as
user through the pipeline settings from the pipeline monitoring page or the pipeline editor. To change the user from the pipeline monitoring page:
Click
Jobs & Pipelines
to open the list of pipelines, and select the name of the pipeline you wish to edit.
On the pipeline monitoring page, click
Settings
.
In the
Pipeline settings
sidebar, click
Edit
next to
Run as
.
In the edit widget, select one of the following options:
Your own user account
A service principal for which you have
CAN_USE
permission
An account group that you are a member of, or that you have
Assume
permission on. See
Set the run-as identity to a group
.
Click
Save
to apply the changes.
When you successfully update the run-as user:
The pipeline identity changes to use the new user, service principal, or group for all future runs
In
Unity Catalog
pipelines, the owner of tables published by the pipeline is updated to match the new run-as identity
Future pipeline updates use the permissions and credentials of the new run-as identity
Like any settings change, the new identity applies to the next pipeline update: continuous pipelines automatically restart with the new identity, while triggered pipelines apply it on their next run. The run-as change can interrupt an active update. See
How configuration changes take effect
.
note
If the update of run-as fails, you receive an error message explaining the reason for the failure. Common issues include insufficient permissions on the service principal.
Set the run-as identity to a group
​
Setting a pipeline's
Run as
identity to an account group works the same way as setting it to a user or a service principal. Pipeline updates run with the group's permissions, and in
Unity Catalog
pipelines the tables the pipeline publishes are owned by the group. Use a group when you want a team to own an automated pipeline rather than tying it to one person's account, so the pipeline keeps working as team membership changes.
In
Databricks
, a role is implemented as a group, so a pipeline whose
Run as
is set to a group runs as that role. See
Role-based access control (RBAC)
.
Setting
Run as
to a group does not change who owns the pipeline. Ownership and the run-as identity are separate settings. To change the owner, see
Change the pipeline owner
.
To configure
Run as
to a group, you must either:
Be a member of the group, or
Have
Assume
permission on the group, if the group is being used for
exclusive access
.
The group must be an account group that is assigned to the workspace. Workspace-local groups cannot be used as a run-as identity, and neither can the broad built-in groups
admins
,
users
, and
account users
.
Grant the group every permission the pipeline needs, as listed in
Required permissions
. Because updates run as the group, granting yourself access to the pipeline's source code and data is not enough.
To set
Run as
to a group in the workspace UI, follow the steps in
How to set the run-as user
and search for the group in the edit widget. Groups appear alongside users and service principals. To confirm the change, reopen the
Pipeline settings
sidebar and check that
Run as
shows the group.

Set the pipeline mode
​
The
Pipeline mode
setting controls how a pipeline processes data:
Triggered
is the default. The pipeline refreshes all tables with the data available when the update starts and then stops, so compute runs only for the duration of the update. Run triggered pipelines on demand or on a schedule. See
Pipeline task for jobs
.
Continuous
keeps tables fresh by processing new data as it arrives in the sources. This reduces the delay between new data and updated results, at the cost of an always-running cluster. Choose continuous mode only when you have a proven low-latency requirement.
To set the mode, use the
Pipeline mode
option in the pipeline settings when you create or edit a pipeline. For a full comparison of the two modes and guidance on choosing between them, see
Triggered vs. continuous pipeline mode
.
How configuration changes take effect
​
When you edit and save a pipeline's settings, the change applies to the next pipeline update. When a
continuous job
orchestrates the pipeline, you don't need to restart the job for the updated settings to take effect; the job applies them on the next update. The job's schedule determines the execution mode, not the pipeline's
Pipeline mode
setting. See
Run a continuous pipeline with a continuous job
.
If you use the pipeline's built-in
Pipeline mode
setting instead of a continuous job:
Continuous pipelines
automatically restart with the updated configuration. This can interrupt an active update.
Changing the type
from triggered to continuous automatically starts a new update with the updated settings. Conversely, changing the type from continuous to triggered cancels an active update.
Choose a product edition
​
Select the product edition with the best features for your pipeline requirements. The following product editions are available:
Core
to run streaming ingest workloads. Select the
Core
edition if your pipeline doesn't require advanced features such as change data capture (CDC) or expectations.
Pro
to run streaming ingest and CDC workloads. The
Pro
product edition supports all of the
Core
features, plus support for workloads that require updating tables based on changes in source data.
Advanced
to run streaming ingest workloads, CDC workloads, and workloads that require expectations. The
Advanced
product edition supports the features of the
Core
and
Pro
editions and includes data quality constraints with expectations.
You can select the product edition when you create or edit a pipeline. You can choose a different edition for each pipeline. For details, including a more comprehensive feature breakdown by edition, see the
Apache Spark™ Declarative Pipelines
on Databricks product page
.
note
Serverless pipelines require the
Advanced
edition. Classic compute supports all editions.
Pipelines retain 60 days of past updates in the pipeline UI and the
Pipelines API
.
Active (non-terminal) updates always appear. If an update is older than the retention window,
Databricks
excludes it from list responses but keeps it in the underlying event log.
Note: If your pipeline includes features not supported by the selected product edition, such as expectations, you receive an error message explaining the reason for the error. You can then edit the pipeline to select the appropriate edition.
Configure source code
​
You can use the asset browser in the Lakeflow Pipelines Editor to configure the source code defining your pipeline. Pipeline source code is defined in SQL or Python scripts stored in workspace files. When you create or edit your pipeline, you can add one or more files. By default, pipeline source code is located in the
transformations
folder in your pipeline's root folder.
Because pipelines automatically analyze dataset dependencies to construct the processing graph, you can add source code assets in any order.
For more details on using the Lakeflow Pipelines Editor, see
Develop and debug ETL pipelines with the Lakeflow Pipelines Editor
.
Manage external dependencies for pipelines that use Python
​
Pipelines support using external dependencies in your pipelines, such as Python packages and libraries. To learn about options and recommendations for using dependencies, see
Manage Python dependencies for pipelines
.
Use Python modules stored in your
Databricks
workspace
​
In addition to implementing your Python code in pipeline source code files, you can use Databricks Git Folders or workspace files to store your code as Python modules. Storing your code as Python modules is especially useful when you have common functionality you want to use in multiple pipelines or notebooks in the same pipeline. To learn how to use Python modules with your pipelines, see
Import Python modules from Git folders or workspace files
.
